# gentle-dot — Channels UX (WhatsApp, phase 1 prototype)

Objective: a **Channels** section in the gentle-dot app (desktop + web) to register and observe the WhatsApp channel, talking to the **external dot-whatsapp bridge** through a minimal daemon proxy. Design: §8 of the study `Propuesta — dot-whatsapp (WhatsApp para Gentle Dot).md` (gentleman/ workspace) + issue [gentle-dot#65](https://github.com/Gentleman-Programming/gentle-dot/issues/65).
Branch: `feat/channels-ux` (cut from beta main, which is ahead 4/behind 3 vs upstream/main by design; rebase before any upstream PR) · Delivery: fork-style prototype first, upstream PR only after #65 gets `status:approved` · Runners: Vitest (`pnpm test`), Playwright (`pnpm e2e`), biome.
Sibling contract: the bridge admin API is specced in the dot-whatsapp repo (`odd/tasks/dot-whatsapp.md`, S6/T8). Both docs share the same endpoints.

## Specs

- **S1 — Channels section with Connectors grammar.** User (L12, dot-whatsapp doc): "en caso de ser aceptado… cómo sería el flujo para que el usuario registre el número de cel, diseñaremos una sesión en la zona de conectores?" → §8: sección **Channels** con la misma gramática visual de Connectors (draft window, aprobación antes de activar, estados `off / pairing / connected / error`). Acceptance: a Channels entry in the UI (desktop and web) shows the WhatsApp card with its live state. Checks: UI tests (vitest), following `ConnectorsPanel.tsx` patterns.
- **S2 — Provider choice.** §8 step 1: "Elegir provider 🟢 Baileys (número dedicado, QR) / 🔵 Meta Cloud API (Business oficial)". Phase 1: only Baileys proceeds; Meta shows as coming soon (the bridge has a stub). Acceptance: wizard step 1 offers both with honest copy. Checks: UI test.
- **S3 — Allowlist, hot-editable.** §8 step 2 + rule: "números E.164 autorizados (el del usuario por default)"; "Allowlist editable en caliente (Engram pineada; la UI solo la edita, sin reiniciar)". Display obeys S7 masking. Acceptance: add/remove numbers from the UI; applied live without restart. Checks: UI tests + fake bridge.
- **S4 — QR pairing in-app.** §8 step 3: "QR grande en la app + countdown + 'regenerar'; credenciales a disco 700". Acceptance: QR renders in-app while pairing, countdown visible, regenerate and cancel work. Checks: UI tests with fake bridge.
- **S5 — Live verification.** §8 step 4: "bridge envía '👋 dot-whatsapp vinculado' al allowlist → Connected si llega". Acceptance: verify action sends and the state transitions per results. Checks: UI tests + fake bridge.
- **S6 — Unpair with confirmation.** §8 rule: "Unpair = cerrar socket + borrar `~/.dot-whatsapp/auth` (700), con confirmación; re-vincular es re-escanear QR". Acceptance: confirmation dialog, then unpair; state returns to `off`. Checks: UI test + fake bridge.
- **S7 — Privacy: masked numbers.** §8 rule: "Nunca mostrar el número completo en logs/UI; últimos 4 dígitos como mucho". Acceptance: the bridge masks server-side; the UI never receives full numbers. Checks: contract test against the admin API payloads.
- **S8 — Honest activation preview.** §8 rule: confirmación antes de activar con preview honesto: "este canal puede enviar mensajes WhatsApp en tu nombre; cada envío al asistente sigue pasando por el approval del usuario". Acceptance: that copy is shown before enabling. Checks: UI test.
- **S9 — Bridge stays external (user decision 2026-10-23: "Externo ahora, hijo después").** Phase 1: the bridge is the external opt-in process it is today (#65: "Gentle Dot itself does not change") and gains a token-authed local admin API on `127.0.0.1`; the daemon gains a **minimal proxy** so the panel works when the bridge runs and shows `off` (not running) otherwise. The daemon never spawns the bridge in this phase; daemon-child integration is proposed later on #65 with this prototype's evidence. Checks: daemon proxy tests with a fake bridge; no child-process code added to the daemon.
- **S10 — Security inherited.** #65 phase 1: E.164 allowlist, anti-loop, text-only DMs. Proxy hygiene: admin token re-read from disk per request (never cached in daemon memory), only `127.0.0.1` targets, bridge errors mapped to clean UI states. Checks: daemon proxy tests.
